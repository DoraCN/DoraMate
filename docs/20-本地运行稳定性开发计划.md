## 文档目标

本文档不讨论新增大块功能，也不讨论更远期的产品能力扩展，只聚焦一个更现实的问题：

> 如何把 DoraMate 当前“浏览器前端 + LocalAgent + DORA runtime”的本地运行主链路，收口为可以反复交付、可以作为发布判断依据的稳定基线。

这里所说的“本地运行主链路”，特指以下三个动作：

- `run`
- `status`
- `stop`

本计划的目标不是让这三个动作“理论上支持”，而是让它们在真实开发环境和真实发布前验证中都具备更高的稳定性、可诊断性和可重复性。

---

## 当前问题定义

结合 `docs/14-本地执行架构设计.md`、`docs/17-DoraMate用户手册.md`、`docs/19-DoraMate项目MVP总结-从可视化编排到本地运行闭环的阶段性复盘.md` 以及 `doramate-localagent/src/main.rs` 当前实现，可以把现阶段问题归纳为以下几类。

### 1. `run` 已可用，但仍偏“成功路径优先”

当前 `run` 已经具备：

- YAML 落盘
- `dora` 安装检查
- runtime readiness 检查
- `dora start` 调用
- 有限重试
- 基础错误码返回

但从发布基线角度看，仍然存在几个明显短板：

- 启动前校验还不够体系化
- 启动失败时的分层诊断还不够稳定
- 部分错误更像“文本错误提示”，而不是稳定契约
- 启动成功后的确认逻辑仍可继续加强

### 2. `status` 已有轮询和状态流，但仍可能出现判断不一致

当前前端已经同时使用：

- WebSocket 状态流
- HTTP 轮询兜底

这是合理的，但还需要进一步回答：

- 哪一个状态源是权威来源
- 当状态流断开时应该怎样降级
- 当进程扫描、缓存状态、UI 展示结果不一致时，以什么为准
- 什么情况下应返回 `Unknown`，而不是误判为 `Stopped`

如果这部分契约不清晰，就容易出现“用户看到已停止，但本地其实还在跑”或“进程已退出，但界面还显示运行中”的问题。

### 3. `stop` 已能触发，但“停止成功”还需要更强验证

当前停止链路已经具备基本功能，但从稳定交付角度看，还需要进一步增强：

- 重复点击停止是否幂等
- 停止不存在或已结束流程时如何稳定返回
- `dora stop` 执行后是否需要二次确认
- 异常停止后如何诊断残留进程和残留状态

对于本地工具来说，“能触发 stop”还不够，必须尽量接近“停止动作可验证、可补救、可复现”。

### 4. 当前缺少足够明确的发布门禁

现阶段仓库中已经有部分单元测试、失败注入测试和 smoke 基线，但对于“本地运行主链路是否足够稳到可以发版”这件事，还缺少一套更集中、更清晰的判断条件。

换句话说，当前更像“有测试”，但还不完全等于“已经形成稳定发布基线”。

## 本次开发原则

本次稳定性开发建议遵循以下原则。

### 1. 不新增大块产品功能

本轮不以增加新界面、新编辑能力或新语言扩展为重点，而是优先收口已有本地执行主链路。

### 2. 先明确契约，再优化实现

如果先改逻辑、后补定义，很容易出现前后端理解不一致的问题。因此应先把状态机、错误码、幂等语义和降级语义写清楚，再推动实现收敛。

### 3. 优先提升失败可诊断性

对当前阶段来说，很多时候“能稳定知道为什么失败”比“偶尔成功一次”更重要。因为只有失败可诊断，后续稳定性才能持续提高。

### 4. 保持前端变更最小化

本轮主要收口点应放在 `doramate-localagent`，前端只做必要配合，例如：

- 展示更稳定的状态枚举
- 展示更明确的错误码
- 在状态过期或未知态时给出合理提示

### 5. 建立真实环境下的最小发布门禁

本轮的终点不是“代码看起来更合理”，而是“每次发布前都能回答 run / status / stop 是否达到最低稳定性要求”。

## 目标状态

本轮开发完成后，DoraMate 本地运行链路应尽量达到以下状态。

### 1. `run` 可分阶段诊断

当 `run` 失败时，应能明确区分失败发生在：

- preflight 阶段
- runtime 初始化阶段
- `dora start` 启动阶段
- 启动等待阶段
- 启动后确认阶段

### 2. `status` 可解释、可降级

当状态源正常时，前端应获得一致、低延迟的状态更新；当状态源异常时，系统也应返回明确的降级结果，而不是误报。

### 3. `stop` 幂等且可验证

停止动作应尽量满足：

- 重复调用结果稳定
- 停止后有验证步骤
- 停止失败后有诊断信息
- 残留状态可被识别

### 4. 发布前可做统一判断

发布前应存在固定的 smoke / integration / failure injection 组合，能回答：

- 这次 `run` 是否稳定
- 这次 `status` 是否可靠
- 这次 `stop` 是否可控

---

## 总体实施路线

建议把本次工作拆成五个阶段推进：

1. 统一状态机与接口契约
2. 加固 `run`
3. 加固 `status`
4. 加固 `stop`
5. 建立发布门禁

这五个阶段应按顺序推进，但其中测试补强和日志规范工作可以尽量伴随每一阶段同步完成，而不是最后一次性补齐。

---

## 阶段一：统一状态机与接口契约

这一阶段的目标不是先写代码，而是把“主链路到底如何定义”讲清楚。

### 1. 统一本地执行状态机

建议在前后端之间统一以下状态集合：

- `Idle`
- `Starting`
- `Running`
- `Stopping`
- `Stopped`
- `Failed`
- `Unknown`

这样做的意义在于：

- 避免不同接口返回不同口径
- 避免前端把“无响应”误当成“已停止”
- 为后续日志和测试建立统一语言

### 2. 明确接口幂等语义

需要分别定义：

- 重复调用 `run` 时如何处理
- 对不存在流程调用 `status` 时返回什么
- 对已停止流程重复调用 `stop` 时返回什么

建议目标是：

- `run` 对同一逻辑会话具备明确冲突处理策略
- `status` 永远返回结构化结果
- `stop` 尽量幂等，不因重复操作变成异常

### 3. 固定错误码体系

当前已有部分错误码和错误信息，下一步应继续整理成稳定集合，建议至少覆盖：

- `DORA_NOT_INSTALLED`
- `WORKING_DIR_INVALID`
- `YAML_WRITE_FAILED`
- `RUNTIME_INIT_FAILED`
- `START_SPAWN_FAILED`
- `START_WAIT_FAILED`
- `START_TIMEOUT`
- `START_CONFIRMATION_FAILED`
- `STATUS_STALE`
- `STOP_TIMEOUT`
- `STOP_CONFIRMATION_FAILED`

错误码的目标不是追求数量，而是让关键失败类型可稳定归类。

### 4. 输出一份接口契约文档

建议产出一份独立的内部说明，明确：

- 状态字段定义
- 每个接口的输入输出结构
- 每个错误码出现的阶段
- 降级语义和幂等语义

这份文档会成为后续实现、测试和前端配合的基线。

## 阶段二：加固 `run` 链路

`run` 是整个主链路的入口，也是用户最容易感知“不稳定”的地方，因此应优先加固。

### 1. 增强启动前 preflight

当前 `run` 已包含部分准备动作，但建议进一步标准化 preflight，至少覆盖：

- `dora` CLI 是否可执行
- 工作目录是否存在
- 工作目录是否可写
- YAML 是否已成功落盘
- runtime 基础快照是否可采集

这一步的目标是尽量把“明显不可能成功”的情况挡在启动前，而不是等到 `dora start` 才暴露。

### 2. 拆分启动阶段日志

建议把 `run` 内部日志明确分层，例如：

- `run.preflight`
- `run.runtime_init`
- `run.start_spawn`
- `run.start_wait`
- `run.start_confirm`

每一层都记录：

- `process_id`
- working directory
- YAML 路径
- 尝试编号
- 耗时
- 错误码
- 错误摘要

这样做能明显提升问题排查效率。

### 3. 加强 runtime readiness 收口

当前 LocalAgent 已经有 `ensure_dora_runtime_ready()` 逻辑，下一步应继续增强：

- 明确 coordinator / daemon 启动顺序与等待窗口
- 对 readiness 检查增加固定超时
- 对恢复动作增加固定退避
- 失败时记录端口快照和关键进程快照

目标不是无限自动恢复，而是在有限恢复后给出可解释失败。

### 4. 保留但收紧重试策略

当前已经存在有限重试，这一思路是正确的，但建议进一步固定：

- 最大重试次数
- 每次重试间隔
- 哪些错误允许重试
- 哪些错误应立即失败

例如：

- runtime 初始化失败，可在有限范围内重试
- 工作目录不可写，不应重试
- YAML 写入失败，不应重试

### 5. 增加启动后确认

`dora start` 返回成功并不完全等于“流程稳定进入运行态”。因此建议新增启动后确认窗口：

- 在固定时间窗口内拉取一次或多次状态
- 只有确认状态离开 `Starting` 或进入 `Running` 才认为成功
- 否则应返回明确的 `START_CONFIRMATION_FAILED`

这一步能减少“命令已返回但实际没跑起来”的假成功。

### 6. 增加并发保护

建议在 LocalAgent 层面对重复点击运行和并发启动做保护，例如：

- 同一 `process_id` 不允许并发 `run`
- 同一工作目录的重复运行需有明确策略
- 同一会话内旧流程未停止时，新流程启动应有清晰反馈

## 阶段三：加固 `status` 链路

`status` 的核心不是“能查一次状态”，而是“长期能给用户一个可信结果”。

### 1. 明确权威状态来源

当前前端使用 WebSocket + 轮询兜底是合理的，但 LocalAgent 内部仍需进一步明确：

- 哪类状态来自实时探测
- 哪类状态来自最近缓存
- 哪类状态属于降级结果

建议在状态响应中增加以下字段：

- `status`
- `last_updated_at`
- `source`
- `stale`
- `message`

这样前端才能区分“正在运行”“状态未知”“状态已过期”。

### 2. 建立 LocalAgent 内部运行注册表

建议在 LocalAgent 内部维护一份最小运行注册表，用于记录：

- `process_id`
- 最近已知状态
- 最近一次成功探测时间
- 最近一次错误
- 当前是否处于 stop 流程

这样可以避免每次状态判断都完全依赖瞬时进程扫描。

### 3. 处理状态源冲突

需要明确这些场景的处理方式：

- WebSocket 断开但轮询正常
- 轮询失败但 LocalAgent 仍保有最近状态
- 进程扫描显示无节点，但 stop 尚未完成
- runtime 有残留进程，但主流程已结束

建议目标是：

- 不轻易误判为 `Stopped`
- 需要时返回 `Unknown`
- 需要时标记 `stale = true`

### 4. 统一状态推送与轮询口径

`status-stream` 和 `/api/status/:process_id` 应尽量复用同一份状态计算逻辑，避免：

- WebSocket 推送一套判断
- 轮询接口再做另一套判断

否则最容易出现“状态流显示 A，轮询返回 B”的分裂问题。

### 5. 增加状态异常的结构化诊断

当状态链路本身异常时，建议不要只返回“failed to fetch status”，而是尽量区分：

- 运行对象不存在
- 状态探测超时
- 状态结果已过期
- 状态源断开

## 阶段四：加固 `stop` 链路

停止能力对本地工具非常关键，因为它直接影响用户是否敢反复试错。

### 1. 明确 `stop` 的两阶段模型

建议把停止流程明确拆成两阶段：

1. 优雅停止
2. 停止后确认与补救

优雅停止阶段负责调用 `dora stop`，而确认与补救阶段负责判断：

- 是否真的停止完成
- 是否存在残留节点
- 是否存在残留 runtime 状态

### 2. 让 `stop` 尽量幂等

应明确支持这些情形：

- 重复点击停止
- 对已停止流程再次停止
- 对未知流程执行停止

理想结果不是全部返回错误，而是尽量返回结构化且稳定的结果，例如：

- 已停止
- 未找到活动流程
- 停止已受理，正在确认

### 3. 增加停止后的验证窗口

建议在 `dora stop` 调用后进入一个短确认窗口：

- 检查状态是否进入 `Stopping`
- 检查节点或 runtime 是否逐步退出
- 在超时后再判定是否进入失败路径

没有这一步，`stop` 很容易变成“命令执行过，但结果不可确认”。

### 4. 加强残留诊断

对停止失败或停止后未完全收敛的场景，建议至少记录：

- 残留节点信息
- runtime 关键进程状态
- 端口占用快照
- 最后一次 `stop` 调用结果

这样即使暂时无法自动恢复，也能提升排查质量。

### 5. 保持补救动作有限且可解释

本轮不建议引入过激的清理策略。更稳妥的方式是：

- 先优雅停止
- 再做有限验证
- 必要时执行有限补救
- 补救失败后返回明确诊断

重点是“可解释”和“可控”，而不是追求全自动强制兜底。

## 阶段五：建立发布门禁

如果没有发布门禁，前面所有加固工作都会在后续迭代中逐步失效。因此这一阶段必须作为正式交付的一部分。

### 1. 补齐关键路径集成测试

建议围绕 `run / status / stop` 增加更集中、更明确的测试集合，覆盖：

- 冷启动运行
- runtime 已就绪时启动
- 工作目录无效
- YAML 写入失败
- `dora start` 超时
- 状态流断开
- 重复 stop
- stop 后残留状态

### 2. 扩大失败注入覆盖面

当前代码中已经存在一定的 forced outcome 测试入口，下一步建议继续利用这类机制，覆盖更多失败路径，而不是只验证 happy path。

### 3. 增加稳定性 smoke

建议增加一组可重复执行的稳定性 smoke，用于连续执行：

```text
run -> status -> stop
```

例如连续执行 20 到 50 轮，并统计：

- 启动成功率
- 状态一致性
- 停止成功率
- 残留率

### 4. 设定发布阈值

建议为发布前验证设定最小阈值，例如：

- `run` 成功率达到预定目标
- `status` 无明显误报停止或误报运行
- `stop` 无不可解释残留
- 所有关键失败都能映射到稳定错误码

阈值不一定一步到位，但必须先定义，才能形成基线。

### 5. 明确环境优先级

建议优先顺序为：

1. Windows 本地真实环境
2. Linux 本地或 CI 环境

原因很简单：当前 DoraMate 的本地开发和实际联调路径与 Windows 环境高度相关，因此应先保证最常用环境的发布稳定性。

## 验收标准

本计划完成后，建议用以下标准判断是否达标。

### 1. `run`

- 能明确区分 preflight、runtime init、start spawn、start wait、start confirm 各阶段失败
- 关键失败场景均有稳定错误码
- 对明显不可恢复错误不再进行无意义重试
- 启动成功后存在最小确认逻辑

### 2. `status`

- 状态接口和状态流使用统一口径
- 状态响应包含更新时间和来源信息
- 状态异常时优先返回 `Unknown` 或 `stale`，而不是误判停止
- 前端不会因单次探测失败立即显示错误终态

### 3. `stop`

- 重复停止具备幂等结果
- 停止后存在确认窗口
- 停止失败时可返回结构化诊断
- 停止后残留状态能被识别

### 4. 发布基线

- 关键路径集成测试通过
- 稳定性 smoke 达到预定阈值
- 真实环境下 `run / status / stop` 具备可重复验证结果

## 主要风险与应对

### 1. DORA runtime 本身的外部不确定性

风险：

- coordinator / daemon 状态不稳定
- 不同环境的启动速度和行为不同

应对：

- 增加 readiness 超时和快照记录
- 用有限重试替代无限恢复
- 把外部问题与 LocalAgent 内部问题分层记录

### 2. 状态判断口径复杂

风险：

- 进程扫描、缓存状态、WebSocket 推送、轮询结果可能不一致

应对：

- 统一状态计算入口
- 为状态增加 `source` 和 `last_updated_at`
- 在不确定时返回 `Unknown`

### 3. 修复稳定性时引入更多分支复杂度

风险：

- 逻辑越补越多，`main.rs` 更难维护

应对：

- 本轮可先保持结构不大拆
- 但要把状态计算、错误码和日志格式尽量抽成明确的小块
- 等基线稳定后再考虑进一步模块化

### 4. 测试环境与真实环境不一致

风险：

- CI 通过但用户本机仍失败

应对：

- 保留失败注入测试
- 增加真实本地 smoke
- 优先把最常用环境做成首要发布基线

---

## 建议里程碑

如果按一个相对紧凑的节奏推进，建议里程碑如下。

### 第 1 周

- 统一状态机
- 整理错误码
- 输出接口契约
- 明确幂等语义

### 第 2 周

- 完成 `run` preflight 加固
- 收紧 `run` 重试策略
- 增加启动后确认
- 补齐 `run` 失败注入测试

### 第 3 周

- 完成 `status` 统一口径
- 引入最小运行注册表
- 增加 `status` 降级字段
- 补齐 `status` 相关测试

### 第 4 周

- 完成 `stop` 两阶段收口
- 增强残留诊断
- 建立稳定性 smoke
- 形成最小发布门禁

## 总结

当前 DoraMate 的本地执行能力已经具备主体闭环，但要把它真正变成“更稳定的发布基线”，重点不是继续堆功能，而是继续收口 `run / status / stop` 这三条主链路。

更准确地说，下一阶段真正要完成的是四件事：

- 把状态机和接口契约讲清楚
- 把 `run` 的失败路径变得可诊断
- 把 `status` 的结果变得可信且可降级
- 把 `stop` 变成幂等、可验证、可补救的动作

当这四件事完成后，DoraMate 的本地运行能力就会从“已经可用”更进一步走向“可以稳定反复交付”，这也是从 MVP 收口迈向更稳发布节奏的必要一步。
