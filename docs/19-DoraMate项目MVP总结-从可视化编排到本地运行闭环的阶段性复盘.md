# 19 - DoraMate 项目 MVP 总结：从可视化编排到本地运行闭环的阶段性复盘

## 1. 文档目的

本文档基于 `docs/00` 到 `docs/18` 的阶段文档、当前仓库目录结构以及现阶段已交付能力，对 DoraMate MVP 做一次收口性总结。本文重点回答以下问题：

- DoraMate 当前 MVP 到底已经完成了什么
- 哪些能力已经形成了真实可用的主链路
- 这次 MVP 实际验证了哪些技术路线
- 当前仍有哪些边界没有完全收口
- 下一阶段应优先补哪些工程项，而不是重复从头设计

本文不是产品宣传稿，也不是新增规划文档，而是基于当前仓库状态的阶段性复盘说明。

## 3. MVP 原始目标回顾

从项目起点看，DoraMate 的 MVP 目标一直比较明确，不是重新实现 DORA runtime，而是在 DORA 之上补齐一层本地可视化工作台，解决以下典型问题：

- 手写 YAML 门槛高
- 节点关系不直观
- 数据流修改后的整体拓扑不易把握
- 本地运行、状态观察和排障反馈不够集中

因此，MVP 的核心任务不是“把画布做出来”，而是把一条最小但真实可用的工作链路串起来：

1. 创建数据流
2. 可视化编辑数据流
3. 保存或导出数据流 YAML
4. 在本地运行数据流
5. 观察运行状态和日志
6. 停止当前运行并回到继续编辑状态

如果上述链路无法成立，DoraMate 就仍然只是编辑器原型；如果这条链路成立，才意味着它开始成为可用工具。

---

## 4. 当前 MVP 已完成的主体能力

从当前仓库实现看，DoraMate 已经完成了“可视化编排 + 本地运行 + 运行观测”的主体闭环，具体可以拆成以下几部分。

### 4.1 可视化编辑器主流程已成立

前端已经具备典型数据流编辑器所需的核心交互，包括：

- 节点拖拽添加
- 节点连线
- 节点属性编辑
- 环境变量与配置编辑
- 多选与框选
- 复制与粘贴子图
- 自动布局
- 撤销与重做
- 最近文件
- 快捷键配置

这说明 DoraMate 当前前端已经不是纯展示型页面，而是具备持续使用价值的编辑器工作台。

### 4.2 YAML 与图模型之间的双向链路已打通

MVP 是否成立，一个关键点在于图形化编辑与 DORA YAML 不能是两套割裂系统。

当前已经形成的能力包括：

- 从 DoraMate 内部图模型生成 YAML
- 从 YAML 回读并恢复可视化图
- 保存布局 sidecar 信息
- 在连线和节点属性变化时同步维护输入映射

这意味着 DoraMate 当前不是“只能导出 YAML 的画图器”，而是围绕同一份数据流语义工作。

### 4.3 LocalAgent 主链路已成立

浏览器不能直接完成文件系统访问、原生对话框调用和本地进程管理，因此 LocalAgent 是 DoraMate MVP 能否落地的关键一层。

当前 LocalAgent 已覆盖的核心能力包括：

- `health`
- `run`
- `stop`
- `status`
- `status-stream`
- `logs`
- 原生目录选择
- 原生文件打开
- 本地文件保存与写入
- 节点模板配置读写

这层桥接的存在，使 DoraMate 从“浏览器中的编辑器”变成“可在本机执行数据流的工具”。

### 4.4 运行观测已形成完整反馈链路

当前运行态反馈不再只是一个按钮状态，而是已经形成完整的状态与日志通路：

- 状态面板
- 日志面板
- WebSocket 状态流
- WebSocket 日志流
- 轮询 fallback
- backlog 回放
- 按级别过滤
- 按节点过滤
- 关键字搜索

这让本地运行过程具备了基本可观察性，而不是纯黑盒。

### 4.5 文件系统工作流已闭环

结合现有前端与 LocalAgent 能力，DoraMate 已经具备一条完整的文件工作流：

- 打开本地 YAML
- 新建空白数据流
- 直接保存
- 另存为
- 导出 YAML
- 管理最近文件
- 管理工作目录

这与 `docs/07-文件系统架构.md` 和 `docs/17-DoraMate用户手册.md` 中强调的纯文件系统路线是一致的。

### 4.6 面向 C# 的语言扩展基础设施已出现

把 `docs/18-Dora C# 绑定开发与集成指南.md` 纳入本轮复盘后，一个重要结论是：DoraMate 当前 MVP 的边界已经不只停留在“编排并运行已有节点”。

当前仓库已经具备：

- `dora-api-csharp` 独立工作区
- C# node 开发能力
- C# NativeAOT operator 开发能力
- Arrow `RecordBatch` 数据面支持
- 样例、smoke 与 regression 验证入口

这意味着 DoraMate 已经开始为多语言节点生态提供真实工程基础，而不只是前端层面的类型占位。

## 5. 从用户路径看，MVP 已闭环到什么程度

如果站在终端用户视角，当前最重要的判断标准依然是：能否把一条数据流从创建走到运行，再从运行走到停止。

从现阶段实现看，这条主路径已经基本成立。

### 5.1 编辑阶段

用户可以在前端中完成：

- 节点添加与删除
- 节点连接与断开
- 参数和配置编辑
- 布局调整
- 多选和复制粘贴

### 5.2 保存阶段

用户可以完成：

- 打开现有 YAML
- 创建新数据流
- 直接保存
- 另存为
- 导出 YAML
- 使用最近文件列表

### 5.3 运行阶段

用户可以完成：

- 选择或设置工作目录
- 触发运行
- 通过 LocalAgent 调用本机 DORA runtime
- 获取运行启动结果

### 5.4 观察阶段

用户可以完成：

- 查看状态面板
- 查看日志面板
- 过滤日志内容
- 观察节点运行状态变化

### 5.5 停止阶段

用户可以完成：

- 停止当前数据流
- 清理本轮运行状态
- 回到继续编辑或重新运行的状态

因此，从用户主线角度给出的结论可以明确表述为：

> 核心路径“编辑 -> 保存 -> 运行 -> 观察 -> 停止”已经形成主体闭环。

---

## 6. 从架构角度看，这次 MVP 验证了什么

MVP 的价值不只是做出功能，更在于验证技术路线是否成立。结合当前实现，可以认为本轮至少验证了以下几件事。

### 6.1 Rust 全栈路线在当前场景下成立

从现有前后端实现看，Rust 全栈路线已经得到正面验证：

- Leptos + WASM 可以承载高交互可视化编辑器
- Axum + Tokio 可以承载本地代理、状态桥接和文件系统接口
- Rust 类型系统足以支撑复杂交互状态与本地运行协作

这意味着 DoraMate 当前不是“为了 Rust 而 Rust”，而是在项目目标下形成了可工作的工程实现。

### 6.2 本地代理模式成立

当前 DoraMate 没有试图让浏览器直接越过边界访问本地环境，而是采用了：

- 浏览器前端
- `127.0.0.1:52100` LocalAgent
- 本机 DORA runtime

这种三层模式已经被证明可用，而且职责边界清晰：

- 前端负责交互、建模和展示
- LocalAgent 负责文件与进程边界
- runtime 负责真实执行

### 6.3 纯文件系统架构成立

当前实现没有引入数据库，而是围绕以下持久化载体工作：

- YAML
- sidecar 元数据
- 本地配置文件
- LocalStorage

对于本地工具型产品，这条路线已经证明具备明显优势：

- 零数据库依赖
- 易于迁移和备份
- 易于排查问题
- 更符合 DORA 以文件为核心的使用习惯

### 6.4 应用级组件体系已具备雏形

前端当前已不只是单页功能集合，而是开始形成稳定的应用级组件组织：

- 工具栏
- 节点面板
- 编辑画布
- 属性面板
- 状态面板
- 日志面板
- 各类对话框和配置入口

这说明项目已经从“把能力堆出来”进入“让结构可持续维护”的阶段。

### 6.5 多语言扩展路线开始被验证

`dora-api-csharp` 的出现说明 DoraMate 当前验证的已经不仅是“可视化编排 + 本地执行”，还包括“多语言节点扩展”这条路线。

当前已经能看到的验证点包括：

- C# node 作为独立进程参与 dataflow
- C# operator 以 NativeAOT 共享库方式参与 runtime
- Arrow 数据面可以跨语言稳定传递
- 样例、smoke 和 regression 形成了验证基线

这使 DoraMate 的定位进一步从“本地可视化工具”扩展到“可承接 DORA 多语言开发工作流的入口平台”。

## 7. 从开发者路径看，MVP 又多走了一步

如果只从终端用户能力来评价 MVP，会低估当前仓库的实际进展。结合 `dora-api-csharp` 工作区，DoraMate 当前已经开始积累开发者扩展路径上的基础设施。

### 7.1 `csharp_custom` 不再只是前端层占位

当前前端里已经存在面向 C# 扩展的节点类型入口，而 `dora-api-csharp` 的存在让这个入口开始具备真实落点：

- 前端负责表达、配置与编排
- C# 工作区负责节点和 operator 的实际开发能力

因此，C# 支持已经不只是界面概念，而是开始具备后端实现基础。

### 7.2 Node 与 Operator 两条开发模型已经被明确区分

当前仓库已经把 C# 扩展明确拆成两种模型：

- 独立 C# node
- C# NativeAOT operator

这种模型区分本身就是成熟度信号，因为它决定了后续模板、脚手架、样例和文档是否能稳定沉淀。

### 7.3 Arrow 数据面已进入可用阶段

当前 C# 绑定不只支持 bytes 或 string，而是已经进入结构化数据可用阶段，包含：

- `RecordBatch` 读写
- schema validation
- contract 校验
- projector
- assertion

这使 C# 扩展线开始具备处理真实结构化数据流的基础。

### 7.4 样例与回归入口提高了可复现性

工程能力的关键不在于“目录里有代码”，而在于“是否有可重复验证的入口”。当前 C# 工作区已经具备：

- `samples/`
- smoke 脚本
- regression runner

因此，本轮 MVP 不只是用户路径闭环，也开始具备开发者扩展路径的可复现雏形。

## 8. 当前仍未完全收口的边界

从当前仓库状态看，DoraMate 已经进入“主体闭环形成，但稳定性和资产化仍需推进”的阶段。仍需继续收口的重点主要包括以下几类。

### 8.1 更严格的真实环境验证仍需继续补强

当前主链路已经建立，但“在更多真实 DORA 环境中持续稳定运行”的验证仍需继续加强。这意味着：

- 主链路可用性已验证
- 基础 smoke 能力已有基础
- 但环境兼容性和长期运行稳定性还需要更多实测支持

### 8.2 LocalAgent 仍需继续加固

虽然 LocalAgent 已覆盖运行、停止、状态流、日志流和文件能力，但距离长期稳定交付仍有继续加固空间，特别是在以下边界上：

- runtime readiness race condition
- timeout 后恢复
- 异常停止后的诊断
- 残留状态与残留进程处理

由于它位于前端与 runtime 之间，任何脆弱点都会直接影响整条用户路径。

### 8.3 面向关键用户路径的自动化回归门禁仍需建立

当前已经存在一定的测试和验证基础，但针对“编辑 -> 保存 -> 运行 -> 观察 -> 停止”这条关键路径，仍需更强的自动化 E2E 回归门禁。

这一步的意义在于：

- 提升后续迭代的发布信心
- 减少跨模块改动带来的回归风险
- 让 MVP 从“可以演示”进一步走向“可以稳定演进”

### 8.4 C# 扩展线仍处于“开发者工作区成熟，产品级接入待推进”阶段

当前 `dora-api-csharp` 已经具备较完整的 SDK、样例和验证入口，但这与“在 DoraMate 前端中形成一键化、模板化、产品级接入体验”仍不是同一件事。

目前已经具备：

- SDK
- 样例
- 构建脚本
- smoke / regression

后续仍需推进的方向包括：

- 更标准化的 node / operator 模板资产
- 与前端编排体验更自然的集成方式
- 面向普通用户的低门槛接入路径

## 9. 本轮 MVP 最值得保留的工程结论

从整个阶段回看，当前 MVP 至少沉淀出以下几条值得保留的工程经验。

### 9.1 本地工具不应被误做成纯前端页面

当前实现说明，把浏览器交互、本地能力和 runtime 执行拆分为三层，是比“前端绕过边界直接做一切”更健康的工程路径。

### 9.2 优先打通主链路，比先做外围精致度更重要

DoraMate 当前最关键的价值，不在于某一个局部功能做得多复杂，而在于优先打通了：

- 打开
- 编辑
- 保存
- 运行
- 观察
- 停止

只有这条主链路成立，后续体验优化才有真实价值。

### 9.3 高交互前端必须重视状态所有权

从前端架构演进可以看到，高频交互系统必须明确：

- 哪些状态局部持有
- 哪些状态由顶层统一管理
- 哪些交互会跨组件传播

这对可视化编辑器类应用尤其重要。

### 9.4 文档必须跟着真实实现走

随着仓库演进，后续文档越来越强调真实实现和当前边界，而不是停留在早期规划叙事。这种转向是必要的，因为只有与代码状态对齐的文档，才能成为可复用工程资产。

### 9.5 多语言扩展要尽早建立可运行样例和验证入口

第 18 篇的经验已经说明，多语言绑定如果只有 API 没有样例、smoke 和 regression，其工程价值会很有限。相反，只要验证入口建立起来，后续模板化和产品化就会有更稳的基础。

## 10. 下一阶段建议优先级

既然 MVP 主体已经成立，下一阶段就不应再把重点放在“从零搭架子”，而应集中在收口、固化和资产化。

建议优先级如下：

### 10.1 优先把本地运行主链路做成更稳定的发布基线

重点不是增加大块新功能，而是继续提升以下动作在真实环境中的稳定性：

- `run`
- `status`
- `stop`

### 10.2 继续加固 LocalAgent

LocalAgent 的稳定性直接决定 DoraMate 是否像一个真正可用的本地工具，因此它应继续作为收口重点，而不是被当作已完成模块长期搁置。

### 10.3 建立关键路径 E2E 回归门禁

如果缺少覆盖主流程的回归门禁，后续每一次前端、代理层或语言扩展改动都可能引入新的不确定性。这一步属于从 MVP 迈向稳定产品的必要条件。

### 10.4 把现有 C# 资产继续向模板化和产品化推进

当前更值得做的，不是重新证明 C# 这条路线“能不能用”，而是继续思考：

- 如何把最小 node / operator 示例沉淀为模板
- 如何让前端更自然承接这些模板
- 如何让 C# 扩展从开发者工作区逐步走向更低门槛的产品能力

---

## 11. 阶段结论

如果用一句话总结 DoraMate 当前的阶段位置，可以表述为：

> DoraMate 已经不再是一个概念验证项目，而是一个核心工作链路已经打通、正在继续做稳定性收口，并开始沉淀多语言扩展资产的本地可视化数据流工具 MVP。

这句话背后对应的是几条明确判断：

1. 可视化编辑器主流程已交付。
2. YAML 双向转换与文件工作流已交付。
3. LocalAgent 本地桥接主链路已交付。
4. 运行状态与日志观测主链路已交付。
5. 项目已进入 MVP 收口阶段，而非基础架构起步阶段。
6. 以 `dora-api-csharp` 为代表的语言扩展基础设施已经出现，并具备真实工程价值。

当然，当前阶段仍不是最终形态：

- 更严格的真实环境验证仍需继续补强
- LocalAgent 仍需继续加固
- E2E 回归门禁仍需建立
- C# 扩展线仍需继续模板化和产品化

但从 MVP 标准来看，DoraMate 已经完成了最关键的一步：

> 它不只是把“可视化编辑”做出来了，而是把“可视化编辑 + 本地运行 + 运行观测 + 多语言扩展雏形”这条更完整的工程主线真正推了出来。
