# 23 - 本地运行门禁与一致性周执行清单

> 适用时间：`2026-04-24` 当周  
> 目标：围绕本地运行主链路，把本周工作收口为四项可执行、可验收、可留档的任务：`CI PR 门禁化`、`多 dataflow 样例 smoke`、`HTTP/WebSocket 一致性校验`、`结果趋势汇总与阈值微调`。

## 1. 本周范围

本周只聚焦已有本地运行稳定性体系的继续收口，不额外扩展新产品能力。相关背景文档：

- `docs/20-本地运行稳定性开发计划.md`
- `docs/21-本地运行状态接口契约.md`
- `docs/22-本地运行发布门禁.md`

本周四项工作的推荐推进顺序如下：

1. 先完成 `CI PR 门禁化`
2. 再扩展 `多 dataflow 样例 smoke`
3. 再补齐 `HTTP/WebSocket 一致性校验`
4. 最后基于新结果做 `结果趋势汇总与阈值微调`

这样安排的原因是：

- 先把门禁入口固定，避免后续工作缺少统一落点
- 先扩样例，再做一致性校验，可以让协议对齐建立在更真实的样例覆盖上
- 趋势和阈值必须建立在本周新增数据稳定产出之后，否则容易对噪声做过度调参

## 2. 本周总体验收口径

到本周结束时，建议至少满足以下结果：

- PR 上已经有明确的本地运行相关 required checks 或等价门禁配置方案
- smoke 不再只覆盖单一样例，而是能稳定跑多个 dataflow
- HTTP 轮询结果与 WebSocket 状态流在相同场景下具备可校验的一致性结论
- `out/release-gates/` 或等价输出目录中已经能够形成可比较的趋势结果
- 当前阈值是否继续维持 `100%`，或是否需要局部放宽，已经有书面依据

## 3. 执行清单

## 3.1 CI PR 门禁化

目标：把当前“可手动执行的发布门禁”推进到“PR 阶段可见、可阻断、可追踪”的状态。

执行清单：

- [ ] 盘点当前已有 workflow、脚本和门禁入口，确认本周纳入 PR 的最小检查集合
- [ ] 明确哪些 job 必须在 `pull_request` 触发，哪些仍保留 `workflow_dispatch` 或更重型入口
- [ ] 将本地运行相关核心检查接入 PR 流程
- [ ] 为关键 job 固定稳定的名称，避免后续 GitHub required checks 频繁漂移
- [ ] 确认失败时能保留足够的日志、summary JSON 或 artifact，便于回看
- [ ] 在文档或 workflow 注释中注明“required checks”对应关系
- [ ] 如果仓库设置 required status checks 需要管理员权限，补一条明确的仓库配置待办

建议最小纳入 PR 的检查：

- 构建或最小单元测试
- 本地运行主链路 smoke
- 本周新增的多样例 smoke 汇总入口

建议产出物：

- 新增或调整后的 GitHub Actions workflow
- 与 workflow 对应的脚本入口整理
- 一份能说明 PR 门禁组成的文档更新或 workflow 内说明

完成标准：

- 新 PR 能自动触发对应检查
- 至少一条失败路径能在 PR 页面直接看出失败原因或下载 artifact 回看
- required checks 名称已经稳定，不依赖临时命名

风险提醒：

- GitHub 仓库层面的 branch protection 往往不完全在代码仓内，需要额外人工配置
- 如果 smoke 运行时间明显增长，需要在“PR 必跑”和“手动重型门禁”之间做分层

## 3.2 多 dataflow 样例 smoke

目标：把 smoke 从单一样例推进到多个代表性 dataflow，降低“单样例通过但真实场景回归”的风险。

执行清单：

- [ ] 盘点仓库内现有可稳定运行的 dataflow 样例
- [ ] 选出本周首批纳入 smoke 的样例集合，优先覆盖不同节点类型或不同编排路径
- [ ] 为每个样例补齐运行前提说明，避免把环境缺失误判为功能失败
- [ ] 让 smoke 脚本支持多样例串行执行，或提供统一汇总入口
- [ ] 在结果输出中记录样例名、轮次、成功率和失败原因摘要
- [ ] 将“默认样例 smoke”和“多样例 smoke”区分成轻量与标准两个档位
- [ ] 对失败样例明确标注是样例本身问题、环境问题还是链路回归

样例选择建议：

- 保留当前最轻量、依赖最少的基线样例
- 新增至少一个不同节点类型的 dataflow
- 新增至少一个更接近真实编排路径的 dataflow

建议产出物：

- 多样例 smoke 脚本或脚本参数扩展
- 样例清单与分档说明
- 汇总结果 JSON 或 Markdown summary

完成标准：

- 一次命令可以跑完首批样例，或通过统一入口批量触发
- 失败时能定位到具体样例，而不是只看到整体失败
- PR 或手动门禁中至少有一个入口使用多样例 smoke

风险提醒：

- 样例扩充过快会把外部依赖噪声引入门禁
- 如果某些样例依赖 GUI、摄像头或额外模型文件，不适合作为 PR 必跑项

## 3.3 HTTP/WebSocket 一致性校验 ✅

目标：验证前端状态消费的两条路径在相同场景下语义一致，避免“HTTP 看起来已停止，但 WebSocket 仍显示运行中”这类漂移。

执行清单：

- [x] 明确同一流程下 HTTP 与 WebSocket 的权威字段和对比维度
- [x] 固定要覆盖的场景：启动中、运行中、停止中、已停止、失败态、未知态或进程不存在
- [x] 补一组自动化校验用例，比较两条通路在同一 `process_id` 下的状态演进
- [x] 统一大小写、别名和降级语义，避免测试层先天不一致
- [x] 对允许存在的瞬时差异设定时间窗口或重试窗口
- [x] 在输出结果中明确记录”不一致样本”的时间点、状态值和通路来源
- [x] 如果存在设计上允许差异的场景，补充到契约或说明文档中

建议重点校验的维度：

- 状态枚举值是否一致
- 状态迁移顺序是否一致
- 终态判定是否一致
- 不存在进程时的返回语义是否一致
- 连接中断或降级时是否遵守既定契约

建议产出物：

- [x] 一组 HTTP/WebSocket 对照测试（6 个单元测试覆盖全部 7 个状态）
- [x] 状态一致性结论记录（docs/21 Section 6）
- [x] 如有必要，对 `docs/21-本地运行状态接口契约.md` 的补充修订（已添加 Section 6 "Allowed Differences"）

完成标准：

- [x] 核心状态场景都有自动化校验覆盖
- [x] 所有允许差异都已书面化，不再靠口头约定
- [x] 对任一不一致结果，都能说明是实现缺陷、契约缺失还是可接受差异

风险提醒：

- WebSocket 天然有时序差异，测试不能要求“绝对同一时刻返回完全一样”
- 一致性测试要重点比较语义，而不是强行比较每一条瞬时事件的到达顺序

## 3.4 结果趋势汇总与阈值微调

目标：基于本周门禁和 smoke 结果，形成趋势视图，并据此判断当前阈值是否需要调整。

执行清单：

- [ ] 统一汇总输入来源，至少覆盖本地 smoke、标准发布门禁和多样例 smoke 结果
- [ ] 固定核心指标：轮次、运行成功率、状态确认成功率、停止成功率、残留失败数、清理失败数
- [ ] 按样例、按脚本入口、按提交或按日期形成可比较视图
- [ ] 标注异常峰值对应的提交、样例或环境背景
- [ ] 判断当前 `100%` 门禁阈值是否仍合理，还是需要对部分非核心指标做微调
- [ ] 记录阈值调整依据，避免仅凭单次失败临时改门槛
- [ ] 输出一版本周结论，明确哪些阈值保持不变，哪些阈值建议调整

阈值调整原则建议：

- 与主链路 correctness 直接相关的指标优先保持严格
- 与清理、副作用或环境噪声相关的指标可以在有充分历史数据时再决定是否微调
- 先增加样本量，再决定是否放宽，不因为单次偶发失败直接降门槛

建议产出物：

- 趋势汇总脚本或汇总文档
- 一份本周门禁数据摘要
- 一份阈值建议表

完成标准：

- 能看出不同样例、不同轮次或不同提交之间的变化趋势
- 每个建议调整的阈值都有数据依据
- 本周结束时可以明确回答“当前 PR 门禁阈值是否适合继续执行”

风险提醒：

- 样本量过小会让趋势结论失真
- 如果本周前半段还在频繁改脚本和样例，后半段汇总时要注意标识数据口径变化

## 4. 推荐推进节奏

如果按一周执行节奏推进，建议顺序如下：

1. 周前半优先打通 `CI PR 门禁化` 与 `多 dataflow 样例 smoke`
2. 周中补齐 `HTTP/WebSocket 一致性校验`
3. 周后半收集结果，完成 `结果趋势汇总与阈值微调`

可以直接按下面的最小里程碑推进：

- 里程碑 A：PR 已能自动跑最小门禁
- 里程碑 B：多样例 smoke 已有首批覆盖并产出汇总
- 里程碑 C：HTTP/WebSocket 一致性已有自动化结论
- 里程碑 D：趋势与阈值建议已有本周留档

## 5. 本周结束时建议留档的结果

为避免工作完成后无法回看，建议本周至少沉淀以下留档：

- 一份更新后的 workflow / 脚本清单
- 一份多样例 smoke 样例列表
- 一份 HTTP/WebSocket 一致性结论
- 一份趋势汇总与阈值建议

如果本周只能先完成部分工作，建议优先保证以下两项落地：

1. `CI PR 门禁化`
2. `多 dataflow 样例 smoke`

因为这两项完成后，后续一致性校验和阈值微调才有更稳定的承载基础。
