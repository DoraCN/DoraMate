# 收尾功能模块实现难度评估

> 基于 DoraMate 项目当前代码状态（2026-05-09）对五个待开发功能模块的评估

---

## 1. Standard 门禁转绿 — 难度：中高

### 现状

门禁体系已相当完整：
- **PR gate**（`local-runtime-pr-gate.yml`）：3 轮，PR 触发
- **Standard release gate**（`local-runtime-standard-release-gate.yml`）：20-50 轮，手动触发，100% 阈值
- 核心脚本 `smoke-localagent-run-status-stop.ps1`：可配置轮次、超时、重试、成功率阈值
- 编排脚本 `release-gate-local-runtime.ps1`：单元测试 + live smoke 一站式执行
- 标准发布要求：100% run 成功率、100% status 确认率、100% stop 成功率、0 残留、0 清理失败

### 卡点分析

当前不是"没有门禁"，而是**门禁不稳定**。失败根因往往不在 DoraMate 自身代码：

| 根因分类 | 典型问题 | 可控程度 |
|---------|---------|---------|
| Dora CLI 自身稳定性 | 进程拉起/停止的竞态条件 | 低（vendored） |
| C# NativeAOT 启动 | 启动时间波动大 | 中 |
| Windows 进程管理 | `taskkill` 行为不确定性 | 低 |
| 状态流时序 | WebSocket 状态转换的时序窗口 | 中 |
| CI 环境 | GitHub Actions Windows runner 资源波动 | 低 |

### 建议策略

属于**系统性打补丁 + 根因分析**，不是单纯开发。需要先做一轮 failure triage：

1. 跑 50 轮 standard gate 收集失败日志
2. 对每次失败按根因分类
3. 按 Pareto 原则（80/20）逐个击破
4. 调整超时参数、增加重试策略、修复 Dora 交互边缘情况

纯开发工作量不大，但**排查和复现成本高**。

## 2. E2E 回归 — 难度：中

### 现状

现有测试覆盖三层：

| 层 | 工具 | 范围 | 状态 |
|---|------|------|------|
| Rust 单元测试 | `cargo test` | localagent + frontend | ✅ |
| C# 回归测试 | `dotnet test` | DoraNode + DoraOperator | ✅ |
| 集成 Smoke | PowerShell 脚本 | 完整 run/status/stop 流程 | ✅ |

**缺失**：前端 → localagent → Dora CLI → 节点执行的全链路 E2E 测试，且没有专门的 E2E 测试框架。

### 关键技术决策

1. **测试框架**：推荐基于现有的 smoke 脚本用 **Pester**（PowerShell 测试框架）包装，避免引入新语言
2. **关键场景**：
   - 创建数据流 → 启动 → 确认所有节点 Running → 停止 → 确认 Stopped → 无残留
   - 异常路径：重复启动、停止不存在的进程、无效 YAML
3. **CI 集成**：PR gate 跑 1 轮快速验证，nightly/scheduled 跑多轮波动检测

### 建议

不需要造轮子，现有基础设施复用程度高。核心工作是**把 smoke 脚本里的隐式断言显式化**为可读的测试用例。

## 3. LocalAgent 残留诊断 — 难度：低-中

### 现状

残留处理已有相当基础：

| 机制 | 说明 | 状态 |
|------|------|------|
| `stale` 字段 | status 响应中标记已过时的状态条目 | ✅ |
| `cleanup_stale_node_processes()` | 根据 YAML 解析节点名并清理 | ✅ |
| `kill_process_by_name()` | 使用 `taskkill /F /IM` 强制终止 | ✅ |
| Stop 超时探测 | 超时后检测残留的 `running_node_ids` | ✅ |
| 烟囱阈值 | `MaxResidualFailures` / `MaxCleanupFailures` | ✅ |

### 差距

现有逻辑是**被动的**（stop 失败后的善后），缺少**主动诊断**：

- LocalAgent 启动时扫描系统中已有 Dora 相关进程
- 端口 52100 被占用时的诊断信息输出
- 上次崩溃留下的 `out/` 目录或 `.doramate.yml` 锁文件检测
- 专门的 `/api/diagnose` 端点输出系统级残留状态

**注意**：现有的 `stale` 标记作用有限 — 标记的是某个 `process_id` 的状态条目已过时，不是系统级残留诊断。

### 建议

- 新增 `/api/diagnose` 端点：扫描进程表、端口、临时目录
- LocalAgent 启动自检：检测并报告异常状态（提供 `--cleanup` 模式）
- 大部分逻辑可从现有代码中提取组合，**预估 2-3 天**

## 4. C# 模板产品化 — 难度：中

### 现状

C# SDK 本身质量很高：

| 维度 | 详情 | 状态 |
|------|------|------|
| API 设计 | DoraNode（同步/异步事件读取）、DoraOperator（NativeAOT） | ✅ |
| Sample 覆盖 | 10 个项目：arrow、async、multi-node、operator 等 | ✅ |
| 回归测试 | DoraNode.RegressionRunner + DoraOperator.RegressionRunner | ✅ |
| 构建脚本 | 13 个 PowerShell 脚本（bootstrap、build、smoke、regression） | ✅ |

### 差距

| 缺失项 | 影响 | 工作量 |
|--------|------|--------|
| **NuGet 包** | 目前是源码引用，用户无法方便引入 | ~2 天 |
| **`dotnet new` 模板** | 不能 `dotnet new dora-node` 快速开始 | ~2 天 |
| **前端模板集成** | `node_templates_config` API 已支持自定义模板，但 C# 未接入 | ~1 天 |
| **Dora CLI 模板** | `dora new` 只有 Rust/Python/C/C++，无 C# | ~1 天 |

### 建议

1. **首要任务**：打包 `DoraNode` 和 `DoraOperator` 为 NuGet 包（`.nupkg`）
2. 创建 `dotnet new` 模板项目（基于现有 samples 裁剪）
3. 将 C# 模板注册到前端 `node_templates_config`（API 已就绪，纯前端集成）
4. 整体预估 **5 天**

## 5. v1.0 发布打包 — 难度：中高

### 现状

| 方面 | 状态 |
|------|------|
| 发布门禁验证 | ✅ |
| 打包/分发系统 | ❌ |
| 版本管理 | ❌（所有组件均为 0.1.0） |
| 升级机制 | ❌ |

### 需要捆绑的组件

| 组件 | 构建方式 | 分发依赖 |
|------|---------|---------|
| LocalAgent 二进制 | `cargo build` | 无 |
| 前端 WASM | `trunk build` | 无 |
| Dora CLI | 目前 CI 中从源码构建 | **需改为预构建二进制** |
| C# SDK | NuGet 包 | 用户本地需 .NET 8 Runtime |
| 示例数据流 | 源码 | 文档 |

### 挑战

1. **Windows 安装包**：MSI/NSIS 的构建和维护成本
2. **.NET 运行时依赖**：C# 节点需要用户安装 .NET 8 Runtime，或捆绑（大幅增加体积）
3. **Dora CLI 分发**：目前 vendored + 从源码构建，需改为独立分发
4. **版本协调**：多组件兼容性矩阵（LocalAgent API 版本 ↔ 前端版本 ↔ Dora CLI 版本）
5. **签名与防病毒**：Windows 二进制不签名会被 Defender/WDAC 拦截

### 建议路径

| 阶段 | 产物 | 说明 | 时间 |
|------|------|------|------|
| **Phase 1** | ZIP 分发 | 二进制 + WASM + 脚本 + README 打包 | 立即 |
| **Phase 2** | NSIS 安装包 | PATH 注册、文件关联、卸载支持 | +3 天 |
| **Phase 3** | 自动更新 | 版本检测、增量升级 | +5 天 |

不推荐 MSI — 对 Rust 项目维护成本过高。

---

## 综合优先级建议

| 排序 | 模块 | 难度 | 预估工期 | 前置依赖 | 理由 |
|------|------|------|---------|---------|------|
| 1 | 残留诊断 | 低-中 | 2-3 天 | 无 | 投入小见效快，同时为门禁稳定性提供数据 |
| 2 | C# 模板产品化 | 中 | 5 天 | 无 | SDK 已成熟，只欠包装；提升开发者体验 |
| 3 | E2E 回归 | 中 | 5-7 天 | 残留诊断（可选） | 为后续门禁优化提供质量守护网 |
| 4 | 门禁转绿 | 中高 | 不确定 | 残留诊断、E2E | 需要前序模块的稳定性数据支持根因分析 |
| 5 | v1.0 打包 | 中高 | 5-10 天 | 门禁转绿 | 发布质量需要可靠门禁保障 |
