# 24 - 本地运行门禁趋势汇总与阈值建议

> 适用时间：`2026-04-24`  
> 目标：基于当前仓库内已经沉淀的 `smoke`、`release gate`、`multi-dataflow smoke` 结果，形成一份可回看、可继续更新的趋势判断与阈值建议。

## 1. 当前结论

截至当前样本，建议结论如下：

1. `run_success_rate`、`status_confirmation_rate`、`stop_success_rate` 继续保持 `100%`，不建议放宽
2. `residual_failures <= 0` 继续保持不变
3. `cleanup_failed_count + out_cleanup_failed_count <= 0` 继续保持不变
4. 多样例 smoke 当前适合继续积累样本，不建议因为早期失败样本而直接降低阈值

核心判断原因是：

- 最新单样例 smoke 结果已经恢复稳定
- 最新标准发布门禁结果通过
- 最新 `baseline` 多样例 smoke 已经 `3/3` 通过
- 当前样本中的失败更多对应“实现尚未收口前的真实回归”，而不是已经确认无法消除的长期环境噪声

换句话说，当前更像“问题被修复并重新转绿”，而不是“系统天然做不到 100%”。

因此，这类失败更适合归类为：

- 真实实现问题，已经被修复

而不是：

- 长期不可避免的环境随机波动

## 3. 当前阈值建议

### 3.1 继续维持的阈值

当前建议继续维持以下阈值不变：

- `run_success_rate >= 100%`
- `status_confirmation_rate >= 100%`
- `stop_success_rate >= 100%`
- `residual_failures <= 0`
- `cleanup_failed_count + out_cleanup_failed_count <= 0`

适用范围建议如下：

- `PR` 轻量门禁：继续保持严格
- 标准发布门禁：继续保持严格
- `baseline` 多样例 smoke：继续按全绿目标推进

### 3.2 当前不建议做的调整

当前不建议：

- 因为本周早期多样例失败样本，直接把成功率门槛从 `100%` 调低
- 因为曾经出现超时，就把 `residual_failures` 或 `cleanup` 阈值放宽
- 在 `standard` 多样例样本还不够的情况下，提前修改发布门禁判定标准

这些调整的问题在于：

- 它们会把“实现尚未完全收口”的问题误判为“指标应该放宽”
- 一旦门槛先降下来，后续就很难知道是真稳定，还是只是被阈值遮住了

## 4. 下一步建议

当前更合理的推进方式不是先降阈值，而是继续补样本。

建议下一步至少补齐：

1. `baseline` 多样例 smoke 再累计 `5` 次绿色结果
2. `standard` 多样例 smoke 至少累计 `3` 次绿色结果
3. 在 PR 门禁运行一段时间后，再回看轻量门禁是否存在稳定噪声

只有在满足以下条件时，才建议重新讨论阈值微调：

- 同一类失败在足够多样本中重复出现
- 失败已确认不是脚本缺陷、样例缺陷或执行组织问题
- 放宽阈值不会掩盖 correctness 层面的真实回归
